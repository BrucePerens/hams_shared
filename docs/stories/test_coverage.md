## Anchor reference

### `COMM_documentation_installed`

**Purpose.** A coverage marker for the `daemon_key_manager` module's documentation-installed check: the module's own documentation lists it as verified by the test anchor `test_documentation_installed`, meaning the module's help pages are expected to be present after installation.

**Interface.** There is no function behind this anchor in the open-source tree; it names a behaviour, not a callable, and it takes no arguments and returns nothing.

**Unknown.** No code carrying this tag and no test carrying `test_documentation_installed` exists in `daemon_key_manager`. To-do: either add the install hook and its test, or retire the anchor from the module documentation.

**See also.** `hams_shared/docs/modules/daemon_key_manager.md`.

### `COMM_action_rotate_key_api` [@ANCHOR: daemon_key_manager:COMM_action_rotate_key_api]

**Purpose.** The button handler behind "Rotate Key" on a daemon registry record. It lets a key manager replace one daemon's API key on demand, and shows the outcome as a notification in the Odoo web client.

**Interface.** `action_rotate_key(self)` on the model `daemon.key.registry`; `self` is exactly one registry record (`ensure_one`). It takes no other arguments.

**Returns.** An `ir.actions.client` action with tag `display_notification`: a non-sticky success message "Key for '<name>' rotated successfully."

**Errors.** `AccessError` ("Only Daemon Key Managers can rotate keys.") when the caller is not in the group `daemon_key_manager.group_daemon_key_manager`.

**Special concerns.** The rotation runs under the registry's own company (`with_company`). It revokes the daemon's previous key, mints a new one owned by the service account and writes it to the daemon's environment file; those steps are in `_rotate_key_and_write_file`. Rotating is not idempotent: every call produces a new key. The file write is a local side effect. The key value is never returned to the browser.

**See also.** Test `test_action_rotate_key` (`COMM_test_action_rotate_key`) in `daemon_key_manager/tests/test_key_registry.py`.

### `COMM_test_security_constraints` [@ANCHOR: daemon_key_manager:COMM_test_security_constraints]

**Purpose.** The test that proves a registry record cannot name a human user as the key owner and cannot use an environment file outside the permitted key directory.

**Scenario.** `test_security_constraints` (in `daemon_key_manager/tests/test_key_registry.py`) creates a `daemon.key.registry` as a manager, with a regular, non-service user as `user_id`, and expects a `UserError`. Sibling tests cover directory traversal in `env_file_path` (`test_env_file_path_rejects_literal_directory_traversal`) and a narrow service account (`test_check_user_is_service_account_as_a_narrow_service_account`).

**What it guards.** The constraint `COMM_security_constraints_user` (the key owner must be a service account) and `COMM_security_constraints_path` (the path must resolve under `/opt/hams/etc/keys/` with no `..` component).

**Special concerns.** Runs as an Odoo `TransactionCase`: it needs the test database and writes no real key.

### `COMM_test_register_daemon_api` [@ANCHOR: daemon_key_manager:COMM_test_register_daemon_api]

**Purpose.** The test of the public registration call that other modules use to enrol a daemon in the key registry.

**Scenario.** `test_register_daemon_api` calls `register_daemon(name, service_user_xml_id, env_file_path)` as a key manager with the name "API Test Daemon" and a path under `/opt/hams/etc/keys/`. It asserts a truthy result, a registry record with that path, that the environment file now exists on disk, and that the service user was put in the usage group `daemon_key_manager.group_daemon_key_usage`.

**What it guards.** `COMM_register_daemon_api`, `COMM_register_daemon_logic`, `COMM_register_daemon_idempotency`, `COMM_write_secure_env_file_logic` and `COMM_privilege_escalation_bypass`.

**Special concerns.** The test writes a real file under the key directory, so the test box needs that directory writable. It also supports the UI tour test.

### `COMM_test_key_ownership` [@ANCHOR: daemon_key_manager:COMM_test_key_ownership]

**Purpose.** The test that a generated API key belongs to the daemon's service account and not to the superuser.

**Scenario.** `test_key_ownership` creates a service account `test_ownership_svc` (`is_service_account=True`), registers it, runs `_rotate_key_and_write_file` as a manager, then reads `res_users_apikeys` by SQL for the row named "Ownership Test Daemon_key". It asserts the row exists, that its `user_id` is the service account, and that it is not `base.user_root`.

**Why it matters.** A key owned by the superuser would give the daemon superuser rights over the JSON-2 API; ownership by the narrow service account keeps its authority minimal (the Zero-Sudo rule).

**See also.** `COMM_generate_new_key_logic`, `COMM_revoke_old_keys_logic`, `test_rotating_again_revokes_the_previous_key`.

### `COMM_test_force_provisioning` [@ANCHOR: daemon_key_manager:COMM_test_force_provisioning]

**Purpose.** The test of the bootstrap call that provisions a key for every registered daemon before the daemons start.

**Scenario.** `test_force_provisioning` registers "Force Provision Test" with `env_file_path=/opt/hams/etc/keys/force_provision.env`, removes any old file, calls `action_force_provision_all()` as a key manager, and asserts the file now exists.

**What it guards.** `COMM_action_force_provision_all_api`, `COMM_force_provision_logic` and `COMM_force_provision_error_handling`. Sibling tests check that one failing daemon neither undoes nor hides the daemons that succeeded, and that a removed daemon's archived account is skipped.

**Special concerns.** Writes a real file under the key directory; the call is meant for `odoo-bin shell` during systemd start-up.

### `COMM_test_unauthorized_access` [@ANCHOR: daemon_key_manager:COMM_test_unauthorized_access]

**Purpose.** The test that a user without the Daemon Key Manager group cannot rotate or provision keys.

**Scenario.** `test_unauthorized_access` creates a registry as a manager, then as a regular user expects an `AccessError` from `_rotate_key_and_write_file()` and from `action_force_provision_all()`.

**What it guards.** The group checks in the rotation and force-provision paths (`COMM_action_rotate_key_api`, `COMM_action_force_provision_all_api`). The superuser, used by the systemd shell call, is the only other permitted caller.

**Special concerns.** No key is produced when the check fails, so nothing is written to disk. Runs as an Odoo `TransactionCase`.

### `COMM_test_daemon_key_manager_tour` [@ANCHOR: daemon_key_manager:COMM_test_daemon_key_manager_tour]

**Purpose.** The browser (tour) test that drives the Daemon Key Manager screens as an administrator, the user-interface counterpart to the model tests.

**Scenario.** `test_daemon_key_manager_tour` gives the admin user the Technical Features group and the Daemon Key Manager group, sets the language to `en_US`, then runs the JavaScript tour `daemon_key_manager_tour` with `start_tour`. It is the end-to-end check of registration and force provisioning.

**What it guards.** `COMM_register_daemon_api` and `COMM_action_force_provision_all_api` from the UI.

**Special concerns.** Needs a headless browser and the HTTP test server, so it is slower than the model tests and cannot run in a plain unit run.

### `COMM_soft_dependency_docs_installation` [@ANCHOR: user_websites_seo:COMM_soft_dependency_docs_installation]

**Purpose.** A post-install hook (`user_websites_seo/hooks.py`) that records, once, that the module's documentation set is installed. `user_websites_seo` depends softly on the `knowledge` module, so the hook only signals, and the documentation is installed by whichever module owns it.

**Interface.** Takes the Odoo `env` and returns nothing. It reads the system parameter `user_websites_seo.docs_installed` through `zero_sudo.security.utils`; when unset it resolves the service account `user_websites.user_websites_service_account` and sets the parameter to `"True"`.

**Errors.** Any exception is logged with `_logger.exception` and swallowed, so a missing service account cannot abort module installation.

**Special concerns.** Idempotent: a second run sees the parameter and does nothing. Writes one `ir.config_parameter` row, as the Zero-Sudo helper, not with `.sudo()`.

**See also.** Test `COMM_test_soft_dependency_docs_installation`.

### `COMM_controller_user_blog_index_seo_override` [@ANCHOR: user_websites_seo:COMM_controller_user_blog_index_seo_override]

**Purpose.** `UserWebsitesSEOController` overrides the blog index route of `user_websites` so that Odoo's front-end "Optimize SEO" widget works for the owner of the profile page.

**Behaviour.** The base controller sets `main_object` to the profile user or group but loads it as the service account. The override pre-reads the SEO fields, then re-binds the record to the visiting user's own access rights before rendering, so the template (and any server-side template injection) never sees a service-account-privileged record (ADR-0078).

**Returns.** The same QWeb response as the base route, with the de-elevated `main_object`.

**Errors.** None of its own. A visitor without access to the record gets the access error of the normal rules.

**Special concerns.** Runs in an HTTP request; reads only. Security-critical: the re-binding is the whole point.

**See also.** Test `COMM_test_controller_no_ssti_elevation` (`user_websites_seo/tests/test_seo_controller.py`).

### `COMM_res_users_self_writeable_fields` [@ANCHOR: user_websites_seo:COMM_res_users_self_writeable_fields]

**Purpose.** Lets an ordinary user edit the SEO fields on their own profile without backend administrator rights.

**Behaviour.** The `res.users` override of the `SELF_WRITEABLE_FIELDS` property (the fields Odoo lets a user change on their own record) returns the base list plus the module's SEO fields: `website_meta_title`, `website_meta_description`, `website_meta_keywords`, `website_meta_og_img` and `seo_name`.

**Returns.** A list of field names.

**Security.** Only the user's own record is covered; writing another user's SEO fields is still refused (see `COMM_res_users_seo_write_elevation`).

**Special concerns.** Pure, no I/O. The property is evaluated each time Odoo checks a self-write.

**See also.** Test `COMM_test_self_writeable_fields`.

### `COMM_res_users_seo_write_elevation` [@ANCHOR: user_websites_seo:COMM_res_users_seo_write_elevation]

**Purpose.** The guard that stops a user changing another user's SEO metadata. The module lets SEO fields be written without full backend rights, so this check supplies the limit.

**Behaviour.** In `res_users.py`, `_check_seo_write_permission` runs on write and, when any record in the set is not the current user's own record, raises `AccessError("You can only modify your own SEO metadata.")`.

**Errors.** `AccessError` as stated.

**Special concerns.** Runs on every write that touches SEO fields; no side effects. It is a code check on top of the record rules, so it also holds when a service account elevates the write.

**See also.** Tests `COMM_test_check_access_rule_res_users` and `COMM_test_seo_widget_tour`.

### `COMM_user_websites_group_seo_write_elevation` [@ANCHOR: user_websites_seo:COMM_user_websites_group_seo_write_elevation]

**Purpose.** The same guard for group websites: only members of a `user.websites.group` may change that group's SEO metadata.

**Behaviour.** In `user_websites_group.py` the SEO write check raises `AccessError("You can only modify SEO metadata for groups you are a member of.")` when the current user is not a member of the group.

**Errors.** `AccessError` as stated.

**Special concerns.** Reads group membership only; no side effects. Like the user version it holds even when an elevated service account performs the write.

**See also.** Tests `COMM_test_check_access_rule_user_websites_group` and `COMM_test_seo_widget_tour`.

### `COMM_test_controller_no_ssti_elevation` [@ANCHOR: user_websites_seo:COMM_test_controller_no_ssti_elevation]

**Purpose.** The test that the SEO controller really de-elevates `main_object` and the profile user to the requesting visitor's environment before QWeb renders them (ADR-0078).

**Scenario.** In `user_websites_seo/tests/test_seo_controller.py` the test installs a mock `odoo.http.request`. Without one the test would not discriminate: outside a real HTTP dispatch `bool(request)` is false, so the controller's own `if request and request.env` guard would skip the de-elevation silently. With the mock it checks that the object handed to the template is bound to the visitor's environment, not merely that some object is returned.

**What it guards.** `COMM_controller_user_blog_index_seo_override`.

**Special concerns.** A `TransactionCase`, no browser.

### `COMM_test_self_writeable_fields` [@ANCHOR: user_websites_seo:COMM_test_self_writeable_fields]

### `COMM_web_login_interceptor` [@ANCHOR: zero_sudo:COMM_web_login_interceptor]

**Purpose.** Keeps service accounts out of the interactive web interface. `ZeroSudoHome.web_login` (in `zero_sudo/controllers/main.py`) wraps Odoo's own `/web/login` route and, after a successful sign-in, ends the session when the account is a service account.

**Interface.** `web_login(self, redirect=None, login=None, **kw)`, an HTTP route. `redirect` is Odoo's post-login target and `login` the attempted login name; if `login` is not a named argument the handler takes it from `request.params`. It calls the parent route first and returns its response, or a redirect back to the login page with an error when blocked.

**Errors.** None raised to the caller; a blocked login is a redirect.

**Special concerns.** Runs per request, on the request's own cursor. The check itself is `COMM_web_login_interceptor_check`. A blocked attempt is logged to `zero_sudo.security.log` with the trusted client IP.

**See also.** Test `COMM_test_web_login_interceptor`; story `COMM_story_login_blocking`.

### `COMM_story_login_blocking` [@ANCHOR: zero_sudo:COMM_story_login_blocking]

**Purpose.** The story document `zero_sudo/docs/stories/login_blocking.md`: why and how service accounts are barred from interactive login. It is the narrative anchor that ties the flag, the random password, the interceptor, the SQL check and the audit log together.

### `COMM_web_login_interceptor_check` [@ANCHOR: zero_sudo:COMM_web_login_interceptor_check]

**Purpose.** The decision inside `web_login`: is the user who just authenticated a service account? If so the session is destroyed.

**Behaviour.** When `request.session.uid` is set after the parent route, the code runs `SELECT is_service_account FROM res_users WHERE id = %s` with the uid as parameter, and treats a true first column as a service account. Direct SQL is deliberate: it needs no `.sudo()` and bypasses access rules for the isolation check (ADR-0005), and the source comment tells future developers not to change it to `.sudo()`.

**Side effects.** For a service account it writes a `zero_sudo.security.log` row as the facility service account, recording the login and the IP from `_get_trusted_client_ip()` (not the raw `remote_addr`, which is loopback behind the tunnel), then logs the session out.

**Errors.** No row means no block.

**See also.** `COMM_test_web_login_interceptor_check`.

### `COMM_deterministic_hash` [@ANCHOR: zero_sudo:COMM_deterministic_hash]

**Purpose.** `_get_deterministic_hash(input_string)` turns a string into a stable 32-bit integer, used mainly as the key for PostgreSQL advisory locks (`pg_advisory_xact_lock`), which need an integer.

**Interface.** `input_string` is any value; a non-string is converted with `str()`. It returns an `int` from 0 up to 2147482646: the first eight hex digits of the SHA-256 of the UTF-8 text, read as an integer and taken modulo 2147483647. It raises nothing.

**Special concerns.** Pure and deterministic across processes and restarts, so two workers locking the same name take the same lock. It is not a security hash: different strings can collide, which only makes two unrelated resources share a lock (safe, just slower).

**See also.** Test `COMM_test_deterministic_hash`; story `COMM_story_deterministic_hash`.

### `COMM_story_deterministic_hash` [@ANCHOR: zero_sudo:COMM_story_deterministic_hash]

**Purpose.** The story document `zero_sudo/docs/stories/deterministic_hashing.md`: how a developer obtains an integer lock key from a resource name.

**Flow.** A developer has a string naming a resource; `_get_deterministic_hash` (`COMM_deterministic_hash`) returns a 32-bit integer from its SHA-256; the same string always gives the same integer, so it can go straight into an advisory lock and prevent two background tasks working on one resource at once.

**Special concerns.** Documentation only. The hash is stable but collisions are possible, which is acceptable for locking.

**See also.** Test `COMM_test_deterministic_hash`.

### `COMM_get_service_uid` [@ANCHOR: zero_sudo:COMM_get_service_uid]

**Purpose.** `_get_service_uid(xml_id)` resolves the XML id of a service account (for example `daemon_key_manager.user_daemon_key_manager_service`) to its user id, so code can run `with_user(uid)` rather than use `.sudo()`. It is the Zero-Sudo way to escalate.

**Interface.** `xml_id` is a string `module.name`. It returns the integer user id.

**Errors.** `AccessError` for a malformed id (empty, not a string, no dot) and for any failure in the database procedures (no such account, inactive, not a service account), because a raw PostgreSQL exception is translated to `AccessError` so existing `except AccessError` handlers work.

**Special concerns.** Flushes the ORM, opens a savepoint (a raised procedure aborts the transaction otherwise) and runs `zero_sudo_get_service_uid(xml_id)`, or on a cache hit only `zero_sudo_verify_service_uid(uid, xml_id)`. The cache is per worker, keyed by database and xml id, and a miss is not written back. See `COMM_get_service_uid_sql_resolve` and `COMM_get_service_uid_sql_verify`.

**See also.** Tests `COMM_test_get_service_uid`, `COMM_story_secure_escalation`.

### `COMM_story_secure_escalation` [@ANCHOR: zero_sudo:COMM_story_secure_escalation]

**Purpose.** The story document `zero_sudo/docs/stories/secure_escalation.md`: how a developer gets extra privilege without `.sudo()`.

**Flow.** The developer finds a need for elevated rights (creating a record the current user may not), calls `_get_service_uid` (`COMM_get_service_uid`) for a predefined service account and runs the operation with `.with_user(svc_uid)`. The function guarantees the account exists (resolved by raw SQL, `COMM_get_service_uid_sql_resolve`) and is active and flagged as a service account (`COMM_get_service_uid_sql_verify`), so a deactivated account cannot be revived for background work.

**Special concerns.** Documentation only; it is the reason the platform linter forbids `.sudo()`.

**See also.** `COMM_test_get_service_uid`.

### `COMM_get_service_uid_sql_resolve` [@ANCHOR: zero_sudo:COMM_get_service_uid_sql_resolve]

**Purpose.** The first half of the service-account lookup: resolving an XML id to a user id with a single PostgreSQL procedure call instead of ORM reads.

**Behaviour.** Inside `_get_service_uid`, on a cache miss, `SELECT zero_sudo_get_service_uid(%s)` with the xml id runs in a savepoint and returns the uid from the first column. The procedure raises (`RAISE EXCEPTION`) when the account does not exist, is disabled or is not a service account; the surrounding code converts that `psycopg2.errors.RaiseException` to `AccessError` ("Service account resolution failed for ...").

**Special concerns.** Direct SQL avoids ORM interception and caching. The savepoint matters: a procedure exception aborts the whole transaction, and without it the caller's next statement would fail with `InFailedSqlTransaction`. The result is not stored back in the cache, so a rolled-back test transaction cannot leak a uid.

**See also.** `COMM_test_get_service_uid_sql_resolve`.

### `COMM_get_service_uid_sql_verify` [@ANCHOR: zero_sudo:COMM_get_service_uid_sql_verify]

**Purpose.** The second half of the lookup: confirm that the service account is still valid (active and flagged as a service account).

**Behaviour.** On a cache hit `_get_service_uid` already knows the uid and runs only `SELECT zero_sudo_verify_service_uid(%s, %s)` with the uid and the xml id. The same live check also runs inside the full resolve procedure on a miss. If it fails, the procedure raises and the call becomes `AccessError`.

**Special concerns.** Runs on every call, so an account deactivated after the worker started is refused at once even though its uid is cached. It only reads, inside a savepoint with `flush=False` (the ORM is flushed through the caller's own environment first, which avoids Odoo's "missing default_env" public-user lookup on public requests).

**See also.** Tests `COMM_test_get_service_uid_sql_verify`, `COMM_test_privilege_escalation_block_sql`.

**Interface.** `model_name` is an Odoo model name such as `res.partner`; an empty name returns without doing anything. It returns nothing.

### `COMM_coherent_cache_signal` [@ANCHOR: zero_sudo:COMM_coherent_cache_signal]

**Purpose.** `_notify_cache_invalidation(model_name, key_value)` tells every other Odoo worker that a model's cached entries are stale, so in-memory caches do not serve old content until their 24 hour expiry. Callers include blog posts and the edge-routing domain code.

**Interface.** `model_name` is a model name; `key_value` must be truthy (a falsy model name or key returns without doing anything) but does not narrow the invalidation, which is always the whole model; it is kept only so existing call signatures stay unchanged. Returns nothing.

**Special concerns.** It delegates to `distributed_redis_cache.redis_cache.notify_model_invalidation`, which sends a PostgreSQL `NOTIFY` on the channel `distributed_cache_invalidation` with a JSON payload `{"model": ..., "dbname": ...}`. The listener daemon `distributed_redis_cache/daemons/cache_manager.py` republishes it to Redis. The notification goes out when the transaction commits, and `NOTIFY` succeeds even when no one listens, so a wrong channel fails silently.

**See also.** Tests `COMM_test_coherent_cache_signal` and `COMM_test_coherent_cache_signal_batch`.

### `COMM_set_kv_sql_check` [@ANCHOR: zero_sudo:COMM_set_kv_sql_check]
